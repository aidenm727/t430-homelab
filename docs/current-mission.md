# Current Mission

## Phase

Engineering Opportunity Intelligence

---

## Mission

Continue evolving Atlas into the primary deterministic engineering interface for the Aiden Platform.

The immediate objective is to design Engineering Opportunity Distinctness Analysis as the next reusable reasoning layer in Engineering Opportunity Intelligence.

This milestone should define how Atlas compares Engineering Opportunity Objects and identifies evidence-backed duplicate, overlap, component, and umbrella candidates without treating lexical similarity as engineering equivalence.

The design must preserve useful distinctions, uncertainty, historical traceability, and human authority over merges and lifecycle mutation.

---

## Current Focus

- Design Engineering Opportunity Distinctness Analysis.
- Define the purpose and ownership of pairwise and portfolio comparison.
- Define duplicate, overlap, component, umbrella, and distinct outcomes.
- Define evidence, counterevidence, provenance, confidence, and ambiguity handling.
- Use capability alignment, scope classification, explicit relationships, references, and object content as comparison evidence.
- Separate deterministic comparison facts from heuristic similarity and semantic judgment.
- Define canonical-target candidate behavior without authorizing merges.
- Preserve stable opportunity identifiers and historical traceability.
- Define integration with Engineering Opportunity Assessment and portfolio reasoning.
- Establish a bounded implementation contract and focused verification cases.

## Current Priorities

1. Define the architectural responsibility of Distinctness Analysis within Engineering Opportunity Intelligence.
2. Define the comparison unit: one ordered or unordered pair of Engineering Opportunity Objects.
3. Define portfolio composition from pairwise findings without duplicate or contradictory results.
4. Define the supported candidate relationship types:
   - `duplicate_of`
   - `overlaps_with`
   - `component_of`
   - `umbrella_for`
   - `distinct_from`
   - `insufficient_evidence`
5. Define directionality and inverse semantics for component and umbrella findings.
6. Define when duplicate and overlap findings are symmetric and when canonical-target proposals are directional.
7. Define how capability alignment contributes supporting or counterevidence.
8. Define how primary scope, scope candidates, and classification uncertainty constrain comparison.
9. Define how explicit dependencies and related opportunities affect distinctness reasoning.
10. Define how shared related documents and evidence contribute comparison signals.
11. Define normalized title, summary, rationale, evidence, and notes comparison boundaries.
12. Define why keyword or token similarity alone can never establish duplication.
13. Define evidence thresholds for candidate, ambiguous, and insufficient-evidence findings.
14. Define negative evidence and boundary evidence that supports distinctness.
15. Define confidence behavior for deterministic, heuristic, and human-reviewed findings.
16. Define how human-reviewed duplicate or merge decisions become authoritative without erasing source identity.
17. Define canonical-target candidate selection and explain why it remains a recommendation.
18. Define merge, close-as-duplicate, retain-separate, clarify-boundary, and review recommendations.
19. Define structured pairwise and portfolio result contracts.
20. Define how Distinctness Analysis attaches to Engineering Opportunity Assessments without duplicating logic.
21. Define canonical object, lifecycle, and repository mutation boundaries.
22. Define the initial implementation boundary and focused verification cases.
23. Register the architecture in Repository Knowledge.
24. Establish deterministic milestone-completion evidence for the design.

## Current Status

The repository now has reusable Engineering Opportunity Intelligence foundations for:

- Object quality and lifecycle consistency
- Structured evidence and references
- Explicit typed relationships
- Canonical capability identity and capability alignment
- Scope taxonomy and bounded scope classification
- Reusable Engineering Opportunity Assessments
- Deterministic milestone-completion reasoning

The Engineering Opportunity Assessment architecture already identifies:

- `duplicate_of`
- `overlaps_with`
- `component_of`
- `umbrella_for`
- `depends_on`
- `enables`
- `supersedes`
- `conflicts_with`
- `related_to`

The repository already supports explicit `depends_on`, inverse `enables`, and explicit `related_to` findings.

However, it does not yet define a complete comparison contract for determining whether two preserved opportunities:

- Describe the same underlying engineering possibility
- Share meaningful scope while remaining independently valuable
- Represent a narrower component and broader umbrella
- Have enough boundary evidence to remain distinct
- Lack sufficient evidence for a responsible conclusion

The repository also does not yet define:

- Pairwise comparison identity
- Portfolio deduplication of comparison findings
- Candidate versus resolved distinctness states
- Evidence and counterevidence requirements
- Scope-aware and capability-aware comparison boundaries
- Canonical-target candidate behavior
- Confidence and ambiguity rules
- Human-reviewed merge authority
- Structured pairwise and portfolio outputs
- Recommendation effects
- A bounded implementation contract

Implementing duplicate detection before resolving these questions would risk collapsing related but valuable ideas and losing repository knowledge.

The next responsible step is therefore to design Distinctness Analysis before implementing it.

## Next Milestone

Design Engineering Opportunity Distinctness Analysis.

Create the architecture contract that defines how Engineering Opportunity Intelligence compares opportunity objects and produces explainable duplicate, overlap, component, umbrella, distinct, ambiguous, and insufficient-evidence findings.

The design should define:

- Purpose and ownership
- Pairwise and portfolio comparison models
- Supported candidate relationship types
- Directionality and inverse semantics
- Duplicate versus overlap boundaries
- Component versus umbrella boundaries
- Distinctness and negative evidence
- Capability-aware comparison
- Scope-aware comparison
- Explicit relationship and document evidence
- Text normalization and heuristic boundaries
- Evidence, counterevidence, and provenance
- Candidate, resolved, ambiguous, and insufficient-evidence states
- Confidence behavior
- Human-reviewed decisions
- Canonical-target candidates
- Recommendation effects
- Structured assessment contracts
- Engineering Opportunity Assessment integration
- Historical traceability
- Canonical object and lifecycle authority
- Initial implementation scope
- Focused verification cases
- Repository Knowledge registration
- Milestone-completion evidence

This milestone should not implement semantic duplicate detection, merge opportunity objects, close lifecycle records, erase stable identifiers, rank opportunities, add command-specific reasoning, or depend on a language model.

## Success Criteria

The milestone is complete when:

- A canonical Engineering Opportunity Distinctness Analysis architecture document exists.
- Pairwise comparison identity and portfolio composition are defined.
- Duplicate, overlap, component, umbrella, distinct, ambiguous, and insufficient-evidence outcomes are defined.
- Directionality and inverse semantics are explicit.
- Duplicate and overlap boundaries are defined.
- Component and umbrella boundaries are defined.
- Capability alignment and scope classification are supporting evidence rather than automatic proof.
- Explicit relationships, documents, and structured evidence have defined comparison roles.
- Text normalization and heuristic similarity boundaries are defined.
- Keyword similarity alone is explicitly insufficient for duplication.
- Evidence, counterevidence, provenance, and confidence requirements are defined.
- Negative evidence and distinctness evidence are defined.
- Canonical-target candidate behavior is defined without authorizing mutation.
- Human-reviewed duplicate and merge decisions remain authoritative.
- Stable identifiers and historical traceability are preserved.
- Reusable pairwise and portfolio result contracts are defined.
- Recommendation effects remain separate from lifecycle and repository mutation.
- Engineering Opportunity Assessment integration is defined.
- The initial implementation boundary and non-goals are explicit.
- Focused implementation verification cases are identified.
- Required architecture metadata is registered in Repository Knowledge.
- Atlas can recognize completion of the Distinctness Analysis design from concrete document evidence.
